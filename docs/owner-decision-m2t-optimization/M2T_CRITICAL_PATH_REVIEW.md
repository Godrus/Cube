## 1. The baselines (and an error in the previous graph)

The previous package reported **75 M2-T tasks and a critical path of 18 tasks (22 with the proposed rule R-MERGE-G1)**. Re-running its generator reproduces 18 and 22. Re-reading it against the acceptance task `XI-02` shows that it was **not a complete acceptance closure**:

| 11 of the 75 M2-T tasks are not reachable from `XI-02`: `VOX-01`, `VOX-04`, `WGEN-02`, `WGEN-04`, `SRV-04`, `CLI-05`, `TEST-02`, `TEST-05`, `TEST-06`, `TEST-09`, `INT-01` | reachability from `XI-02` | acceptance did not depend on the voxel backend that executes edits, on the generation service, on replication |
| reload after restart (T-08) needs recovery from base + snapshot (`PERS-06` in the ADG), which v1 moved to M2 | `world-persistence-contracts.md` WP-08 order; v1 difference D-4 | the M2-T criterion could not be met by the graph |

Three graphs are therefore compared:

| Graph | M2-T tasks | Strict chain (tasks) | Chain with R-MERGE-G1 | Edges | Levels | Max width |
|---|---|---|---|---|---|---|
| **v1** as committed | 75 | 18 | 22 | n/a (incomplete) | | |
| **B1**: ADG-faithful and acceptance-complete (v1 plus the missing acceptance edges and the persistence chain `PERS-04`, `PERS-05`, `PERS-06`, `TEST-04` that the ADG requires for reload) | 79 | **20** | 24 | 426 | 24 | 12 |
| **v2**: proposed optimisation (OPT-01...OPT-08) | **74** | **18** | **22** (21 if INT-01 is excluded from the rule) | 350 | 22 | 15 |

Reading: against the honest baseline B1, v2 has **5 fewer tasks in M2-T (79 -> 74)**, a **2-task shorter strict chain (20 -> 18)**, **76 fewer dependency edges (-18 %)**, and **wider parallelism** (up to 15 tasks at one level against 12). The equal number 18 for v1 and v2 is a coincidence of two different graphs. **Task-count changes and critical-path changes are separate figures**: removing tasks that are off the chain (for example `NET-02`) reduces the first, not the second.

Honest limit: the strict chain shrinks only by 2 because it is dominated by things that cannot be removed: governance (4 tasks), the Core chain (`CORE-01`, `CORE-03`, `CORE-06`, `CORE-10`), the persistence chain, and the runtime sequence. The larger benefit of the optimisation is in **fan-in and parallelism**, not in the chain length.

`GOV-01 -> GOV-04 -> GOV-06 -> TEST-01 -> CORE-01 -> CORE-03 -> CORE-06 -> CORE-10 -> API-01 -> API-04 -> PERS-01 -> PERS-02 -> PERS-03 -> PERS-06 -> SRV-01 -> SRV-03 -> SRV-04 -> XI-02` (18 tasks).

## 2. Local authoritative runtime (the model behind the NET/SRV reductions)

**Question:** can M2-T use a local authoritative runtime with no mandatory network transport, dedicated server or session management, without creating a throw-away implementation?
**Answer (proposed, ODM-16): yes, because the recorded architecture already says so, provided the interface is message-shaped.** Sources: AOD-22 (single-player starts the same authoritative runtime in the client process; embedded and dedicated differ only in start and lifecycle; the embedded server uses an in-process transport; semantics identical; no client-only authoritative mode), SR-01/SR-02/SR-06/SR-08 of the Draft server contracts.

| # | Property of the M2-T local runtime | How it is satisfied |
|---|---|---|
| L-1 | one authority for world mutation | `SRV-03` single-threaded fixed-step writer; every edit is a user commit through `IEditingService` (`ORCH-05`, AOD-15) |
| L-2 | a clear World Operations interface | `TGAP-03a`: typed commands in (edit request, player intent, session open), views out (chunk data, player state), events out; plain data with no references or callbacks into runtime state |
| L-3 | no mandatory network transport | the embedded client uses `NET-03` (a channel pair implementing the `NET-01` trait); no carrier, no encoding |
| L-4 | no dedicated server, no multi-session management | `SRV-08`, `SRV-02`, `SRV-05..07` are not built; the local player is the one session, with an `AuthorizationContext` minted by the embedded host (SR-06, SR-08) |
| L-5 | persistence through the authoritative runtime | `SRV-01` owns the persistence service (SR-10); the client never touches storage |
| L-6 | mutation semantics documented and testable | `CORE-06` commit semantics, `ORCH-03` expected-token validation, `TEST-10` negative tests |
| L-7 | not a separate implementation to discard | the runtime is exactly `SRV-01`/`SRV-03`/`SRV-04` of the ADG; only the carrier, the wire encoding, authentication providers, reconnect, permissions and the dedicated host are deferred; later tasks add around the runtime, not instead of it |
| L-8 | compatible with remote execution | messages carry `OperationId` and `ActorKind`; the client keeps a cache and never mutates world state; a **serialising loopback adapter** (small, M2) proves that the messages serialise, and the conformance suite of SR-09 later runs on both transports |

**Migration path to multiplayer:** `NET-02` (wire protocol, handshake and authentication encoding, versioning) -> `NET-04` (external transport, after the `SPK-NET` spike and the owner's choice `GOV-12`) -> `SRV-02` (authentication integration) -> `SRV-05/06` (reconnect, permissions) -> `SRV-08` (dedicated host) -> `CLI-05` (prediction and reconciliation). None of these changes the World Operations interface; they implement what it already names.

**Rejected alternative (direct calls, no transport boundary at all):** removing `NET-01` and `NET-03` entirely leaves the strict chain at **18 (computed)**, i.e. it gains nothing in the metric while it would create a second access path and ignore AOD-22 (6). Therefore both stay, as a contract (`NET-01`) and a thin binding (`NET-03`).

## 6. Options considered and not recommended

| Option | Computed effect | Why not |
|---|---|---|
| remove `NET-01`/`NET-03` entirely | chain 18 (no gain) | second access path; conflicts with AOD-22 (6) |
| split persistence wiring out of `SRV-01` into integration | chain 18 (no gain) | coherence of `SRV-01` (SR-03: start performs recovery) |
| start `PROC-01` before `CORE-10` (earlier "read-only" freeze) | none on the v2 chain (Processing is off it) | weakens the single freeze event for no gain |
| decouple `TEST-01` from the start of `CORE-01` (ODM-17) | none in the strict metric (archcheck is a required check) | overlap only, a plan amendment |
| drop `INT-01` from R-MERGE-G1 | 22 -> 21 with the rule | a status record should not gate code merges; part of ODM-14 |

## 7. What remains on the path and why

Governance (4 tasks) cannot be shortened by engineering; Core (4) is the foundation; `API-04 -> PERS-01 -> PERS-02 -> PERS-03 -> PERS-06` is the real binding branch (it also contains the experiment `SPK-PERS`, which can run now); `SRV-01 -> SRV-03 -> SRV-04` is the runtime. Further shortening would need a **different persistence design** (for example writing the first snapshot format inside `API-04`'s phase), which is an architecture change and is not proposed.
