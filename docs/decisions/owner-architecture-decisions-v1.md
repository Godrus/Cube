# Owner Architecture Decisions v1

**Status:** Approved Owner Decisions (AOD). AOD-01…19 were recorded from the owner's instruction in chat on 2026-11-04; AOD-20…24 were recorded on 2026-11-05 (section 5), both for the docs-only branch `docs/architecture-roadmap-v1`. AOD-24 is **Conditionally Approved**; all others are Approved. The owner should confirm this record when the branch is merged.
**Scope:** technology, boundary and process decisions needed to go from the current Rust + Godot spike to a full voxel RPG/MMORPG. This record **does not approve any API contract**, does not decide any ACR (ACR-004 is prepared as **Pending**, see section 5), does not edit AU-1.0 and does not close any blocker. It extends [`owner-decision-rust-godot.md`](owner-decision-rust-godot.md) (which stays valid).
**How to read the "Today" column:** it states what the repository demonstrates now (spike branches), so that an approved decision is never mistaken for an implemented one.

### 5.1 AOD-20 WorldGen to Core (OAM-01), Approved

* **Scope:** the write path and ownership of procedurally generated terrain relative to Core, the Editing API and the server.
* **Approved:** hybrid option C, realised as **variant C3** (hybrid system generation, Editing API for user changes, a separate persistence strategy per AOD-21). Concretely: (1) procedural generation creates the base world through a dedicated WorldGen/System-commit boundary; (2) WorldGen is not an ordinary user Editing-API operation; (3) user terrain changes pass only through the Editing API; (4) the server owns the authoritative world state; (5) initial generation does not enter ordinary undo/redo; (6) system generation receives an OperationId and takes part in revision/commit semantics; (7) WorldGen never bypasses the public Core/system-commit ports.
* **Not approved:** the system-commit port signature and error set; how a system commit advances revisions (the same RevisionToken scope or a separate generation epoch; B-6 stays open; the earlier proposal of a separate generation revision in [`worldgen-core-boundary.md`](worldgen-core-boundary.md) is therefore only a candidate); whether the Core keeps generated and user data in one layer (C1) or in two layers (C2 overlay), see OAM-09 (`Recommended / Requires Owner Approval`: C1; C2 Deferred); the persistence model is AOD-21, not a C-variant; chunk delivery to clients (data versus seed + version); whether system operations are kept in an audit log; any code, contract text or Core type change.
* **Consequences:** the spike's direct commits (streamer, `edit_voxel`, `fill_box`, spike undo journal) remain experimental and non-compliant; three writers only (Editing service, WorldGen Materialiser via the system-commit port, persistence loader); Core gets a new public port and an operation origin for system operations; history must exclude system operations; the server runs WorldGen.
* **Contract changes needed (all Draft, nothing edited now):** C-17 OperationId (origin: user or system), the commit primitive and RevisionToken contracts (system scope; B-6), a new WorldGen port and a new system-commit port contract, the history rule in the E-series (exclusion of system operations), persistence contracts (AOD-21), replication of baselines (Gate 7).
* **Verification criteria:** a call-site audit test showing that only the three writers reach the commit port; a dependency test that WorldGen sees no Core internals beyond the ports; determinism and pinned-hash tests; a history test that generation cannot be undone; revision tests for system commits; an authority test that a client cannot invoke the system-commit port; idempotent materialise and evict.
* **ACR:** **ACR-004 prepared, status Pending** ([`audit-resolution-report.md`](audit-resolution-report.md), Architecture Change Requests). Reason: AU-1.0 defines neither a WorldGen module nor a system actor, and a new public Core port plus a system OperationId are placement and semantics changes. AU-1.0, ACR-001/002/003 are not edited.

### 5.2 AOD-21 Persistence (OAM-02), Approved

* **Scope:** the model of persistent world state for single-player and server. It refines AOD-17 (it does not replace it).
* **Approved:** (1) an untouched world is stored as `WorldSeed + GeneratorVersion`; (2) user changes are stored in a durable mutation journal; (3) the journal is compacted periodically into chunk snapshots; (4) snapshots speed up loading and are not the only source of truth; (5) the journal survives sudden process termination; (6) load order is `base generation, then snapshot, then journal tail`; (7) a change of GeneratorVersion never silently changes an existing world; for an old generator version the world uses a pin or an explicit bake/migration.
* **Not approved:** any binary format, concrete database or storage engine, exact file fields; journal granularity (voxel deltas versus operation intents); record, snapshot and manifest schemas; compaction trigger and retention policy; flush policy and its numbers; which of pin, bake or migrate applies to a given world (only that the choice is explicit); the local single-player store location. `world-state-v0` remains experimental and temporary.
* **Confirmed compaction protocol (Approved architecture, 2026-11-05):**
  `write snapshot, then fsync snapshot, then verify snapshot, then atomically update the manifest, then fsync the manifest, then compact/truncate the journal only after successful verification.`
  Rules: (1) a snapshot is never the only source of truth before it is verified; (2) the previous snapshot is kept until the new one is activated; (3) the journal tail is kept until the new recovery point is confirmed; (4) a crash between any two steps leaves a recoverable state; (5) a snapshot records its base generator version and its revision boundary; (6) a change of GeneratorVersion never changes an existing world silently; (7) compaction is idempotent; (8) recovery must check hash, epoch, revision and generator version. The step-by-step crash analysis is in [`docs/api-contracts/world-persistence-contracts.md`](../api-contracts/world-persistence-contracts.md) (WP-07, WP-08, Draft).
* **Still Proposed or Spike Required:** the binary formats, the concrete database or storage engine, the exact fields of journal/snapshot/manifest files, the hash algorithm, the platform mechanism for durable writes and atomic replacement on Android and iOS, retention numbers and flush policy.
* **Consequences:** the persistence contracts and the `cube-persistence` spike must be reconciled (OI-4); the generator-version registry and old generators (or baked data) must stay available for every saved world; crash recovery tests become part of Gate 5.
* **Contract changes needed (Draft):** rewrite of P-01…P-09, `IDeltaStore`, `ISnapshotStore` (world record with seed and generator version, journal, snapshots, manifest, load order), a mutation-journal contract, a generator-version and migration contract. A first Draft exists: [`docs/api-contracts/world-persistence-contracts.md`](../api-contracts/world-persistence-contracts.md).
* **Verification criteria:** fault injection at every step boundary of the compaction protocol; verification that recovery checks hash, epoch, revision and generator version; kill-during-write recovery and truncated-tail tolerance; idempotent repeated compaction; journal replay equals live state; `snapshot + journal tail` equals full replay; recovery without any snapshot; version-mismatch refusal (no silent change); migration rehearsal for a generator bump; storage growth and replay time measured on a device.
* **ACR:** none required by this decision alone. If the rewrite of the persistence module description conflicts with an AU-1.0 clause, a new ACR is prepared then.

### 5.3 AOD-22 Embedded Server (OAM-03), Approved

* **Scope:** the hosting model of the authoritative server runtime.
* **Approved:** (1) single-player starts the same authoritative Rust server runtime inside the client process; (2) the dedicated server uses the same runtime in a separate process; (3) no client-only authoritative mode is introduced; (4) transport, persistence and authority boundaries are the same; (5) embedded and dedicated differ only in how they are started and in lifecycle. **Confirmed 2026-11-05:** (6) the embedded server uses an **in-process transport**; (7) the dedicated server uses an **external transport**; (8) the transport implementations may differ, but the semantics of protocol, authority, authentication, authorization, OperationId, revision and conflict rules are identical; (9) the embedded mode gets no special rights and does not become client-authoritative; (10) the conformance tests run on **both** transport implementations.
* **Not approved:** the transport itself (OAM-05); the external transport of the dedicated server (OAM-05 `Spike Required`: TCP, QUIC/UDP, an existing library and a control/data split are all undecided); the crate and module placement of the runtime in the layer grid; the local store; the conditions for moving a world from embedded to dedicated (they stay a proposal in the matrix); mobile feasibility of the embedded runtime (needs a physical-device measurement).
* **Consequences:** the server must be a library with a thin host (process wrapper or in-process launcher); one conformance test suite that runs on both transport implementations ([`docs/api-contracts/server-runtime-contracts.md`](../api-contracts/server-runtime-contracts.md), SR-09, Draft); AOD-05 remains valid; on mobile the embedded mode is the only mode compatible with AOD-12 (no child processes).
* **Contract changes needed (Draft):** a server-runtime lifecycle and host contract, the transport abstraction (with OAM-05), authority contracts in the Editing/Server series, persistence ownership by the runtime. A first Draft exists: [`docs/api-contracts/server-runtime-contracts.md`](../api-contracts/server-runtime-contracts.md); the WorldGen and system-commit drafts are [`worldgen-contracts.md`](../api-contracts/worldgen-contracts.md) and [`system-commit-contracts.md`](../api-contracts/system-commit-contracts.md).
* **Verification criteria:** the same conformance and authority tests pass on the in-process and the external transport and against both hosts; a client cannot commit in either mode; persistence parity (a world saved by one mode loads in the other); no code path that lets the client write authoritative state.
* **ACR:** none now; placing the server runtime in the AU-1.0 module grid may need one and is not filed.

### 5.4 AOD-23 Licence and sources policy (OAM-07), Approved

* **Scope:** use of third-party projects and sources in Cube's design, code and assets.
* **Approved:** (1) Veloren code and assets are not copied; (2) a GPL project is used only as an architectural reference; (3) CubeWorld-Reversal is research material only; (4) reverse-engineered code, assets, original implementation names and decompiled algorithms are not carried over; (5) architectural ideas are re-thought and implemented independently; (6) legally sensitive cases are marked as requiring separate review.
* **Not approved:** Cube's own licence; the licence list for dependencies; any deeper study method for the reverse-engineered repository beyond what the research notes already record (such a case is marked for separate review).
* **Consequences:** documents keep evidence labels (fact, inference, recommendation, decision, hypothesis); dependencies are listed with licences before adoption; copied or closely paraphrased third-party code is a defect.
* **Contract changes needed:** none.
* **Verification criteria:** a review checklist for pull requests (no third-party code, assets or names; dependency licence recorded); a search of new code for upstream identifiers; research notes carry no reverse-engineered names.
* **ACR:** none.
