# Visual QA v2: calibration design (experimental)

State: offline-validated; **2 live attempts so far (1 answered, 1 service error)**; no accuracy has been measured. v1 questionnaires and v1 results are kept unchanged (`questions/*.json`, `results/2026-11-10-first-live/`).

## 1. Why v1 failed (analysis)

Live run 1 (5 images): 3 of 5 verdicts right, both good screenshots wrongly FAIL.

| v1 check | what went wrong | cause in the question |
|---|---|---|
| `tears_in_terrain` | yes (0.75 to 0.89) on both good frames | "sharp gaps or cracks" is true of healthy Cube terrain: steps, cube edges and exposed side faces are everywhere |
| `large_hole_in_ground` | missed the painted hole (0.33), fired on a good frame (0.76) | the hole was filled with sky colour, and the world has a finite edge where dark background legitimately shows; "background where ground should be" cannot be told from that edge without a reference |
| `voxel_ground_visible` | 0.53 on one normal frame | the threshold (0.7) is strict for a question that is only mostly true |
| fixtures | synthetic edits, 3 defect images, 2 good ones | too few, one of each kind, ambiguous labels fixed partly after the results |

Also v1 asked the model about things code decides exactly (a black frame, a flat colour).

## 2. v2 design

- **Code decides what code can decide** (`deterministic.py`): image size, black or flat frame, batches delivered, loaded bricks against a reference, scene updated after an edit. On the fixtures these catch **all** partial loads (17 of 83 and 29 of 77 bricks) and **all** stale updates (pixel difference 0) without a model.
- **TypeSafe only for what is visual and semantic** (`questions/v2/`): is block terrain visible, which kind of scene, a patch of ground where background shows through *with ground around it*, a block-shaped patch of an off-palette colour, and for edits a missing block in an enlarged crop. Normal steps, cube edges, side faces, height changes and the finite world edge are stated as normal in the descriptions and are never asked about.
- **Box only after a presence question** (`gap_in_ground` gates `gap_box`, `block_missing_in_after` gates `notch_box`); the Box answer counts only when the presence answer is >= 0.7.
- **Block edit** uses a 4x nearest-neighbour enlargement of the 25 % square around the crosshair (the known edit area), before and after, with the operation known to the scenario. A single removed block is about 0.02 % to 0.06 % of the frame (18 to 590 changed pixels), which is why the whole frame is not used.

## 3. v1 vs v2 by question construction (no accuracy claim)

| aspect | v1 | v2 |
|---|---|---|
| questions about "damage in general" | yes (tears, holes) | none; localized signs only |
| treats normal Cube terrain as possible defect | yes (by wording) | explicitly normal in the description and not asked |
| empty / black / flat frame | asked of the model | code |
| scene type | Choice with 4 options | Choice with 3 (`block_landscape`, `blank_or_background_only`, `other_scene`) |
| Box | none live | gated by a presence Noul; compared with the pixel difference to the good picture |
| edit | whole frame, two images | enlarged crop of the known edit area, operation known, expectation is a parameter |
| images | 5, synthetic defects | 37 usable pictures from the real scene, controlled faults |
| labels | partly after the answers | per fixture, written from what the scene did and from pixels, committed before any v2 request (commit 8988b36) |

## 4. Fixtures (`fixtures-v2/`, made by `make_godot_fixtures.py`, labels by `label_fixtures.py`)

Faults are applied to the **Godot scene** by QA options of `godot/main.gd` (free a brick node from the scene, hide four bricks, tint a brick blue, stop delivering batches after one frame, skip the update after an edit). The Rust world and the renderer are not changed.

| split | good | missing_brick | hidden_area | wrong_material | partial_load | edit changed | edit stale (unchanged) |
|---|---|---|---|---|---|---|---|
| calibration (seeds 101-104, 301-305) | 4 | 2 | 2 | 1 | 2 | 1 | 2 |
| evaluation (seeds 105-108, 306-310) | 4 | 2 | 2 | 2 | 2 | 1 | 3 |
| excluded by pixel rules | 0 | 0 | 0 | 1 (no visible change) | 0 | 2 (no visible change) + 1 (edit missed) | 0 |

Scene pictures 23 (8 good, 15 defective); edit pairs 7 (28 % of the pairs are real edits: 2 of 7), 14 images; **37 usable pictures**. Defective pictures outnumber good ones by about 2 to 1, and the edit set has only two positive pairs: both limits are visible in any result. The calibration set may be used to change questions and thresholds; **the evaluation set must not**.

## 5. Box check (the only live use in this stage)

Two requests were allowed; both were attempted:

1. `seed101-missing_brick` (calibration), answered: presence `gap_in_ground` = **0.60** (below the 0.7 gate, so the Box would not be shown in production), `terrain_visible` 0.87, `scene_kind` block_landscape 1.00, `off_palette_patch` 0.32. The Box itself (confidence 0.24, ungated, informational): `top 0.35, bottom 0.99, left 0.19, right 0.77` against the pixel-difference box of the defect `0.177, 0.35, 0.777, 1.0`: IoU **0.95**, centre offset 0.006. Caveat: the true box covers 39 % of the picture (the missing brick changes a large area), so a large box scores well easily; this does not show fine localisation.
2. `seed102-hidden_area`: **HTTP 529 `system_overloaded`** from the service. Not retried (the allowance was two requests).

Conclusion: no evidence yet that Box gives useful localisation (one sample, large target, presence check below its gate, low confidence). **Box stays out of any production QA.** Tokens used: 2,910 input and 122 output for the answered request. Files: `results/2026-11-10-v2-box/`.
