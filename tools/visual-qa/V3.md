## Generated is not executed

`counts.generated` and `counts.executed` are separate numbers in every report. `--execute none` generates and plans only (executed 0). A scenario counts as executed only when every Godot phase finished and wrote telemetry.

## What a scenario is

Plain data (`scenario_gen.py`): id, category, template, generator version, generator seed, world seed, intensity, phases (each phase is one Godot process; a second phase can reopen the same world directory), the steps (`wait`, `move`, `turn`, `shot`, `edit`, `probe`, `fault`, `freeze`, `occlude`), the deterministic expectations, the injected fault (if any), the TypeSafe questions with the expected answer, and a fingerprint (sha256 of the canonical scenario). Scenario *i* depends only on (generator version, seed, i, template); generating 5 or 30 gives an identical scenario 3 (tested). The template of scenario *i* is the profile's list in fixed order (no hidden shuffle). Godot runs with a fixed time step (1/60), so a scenario does not depend on frame timing.

## Categories actually supported

| Category | Templates (all executed in Godot) | Deterministic checks | TypeSafe role |
|---|---|---|---|
| CAMERA | `cam_top`, `cam_up` (looking up), `cam_horizontal`, `cam_angled`, `cam_rotate` (90, 180 or 360 degrees), `cam_move` | commanded pitch and yaw reached (tolerance 0.03 rad), position unchanged by a turn, climbed, moved along the heading, sky fraction range, after a 360 turn the picture equals the start picture | confirm (asked only with `--compare` or `--force-typesafe`) |
| WORLD | `world_view`, `world_restore` (reopens the saved world), `world_partial_load` (injected), `world_missing_brick`, `world_hidden_area`, `world_wrong_material` (injected) | bricks loaded, frame not black or flat, restore: same brick count and identical picture, partial load found by brick ratio below 0.95, injected fault visible (>= 0.2 % of the frame, else the scenario is excluded: label unreliable) | **primary** for the 3 injected faults (code cannot see a missing patch in one picture); none for partial load |
| EDITING | `edit_remove`, `edit_place`, `edit_series`, `edit_persist` (edit, close, reopen the world, same picture) | every edit hit, bricks rebuilt after the edits, picture changed (warn if rebuilt but identical), persistence by picture | confirm (the v2 block-edit question missed both real edits) |
| OCCLUSION | `occ_panel_opaque`, `occ_panel_translucent` (UI panel over the middle), `occ_object_in_front` (3D box in front of the camera), `occ_hud_corner` (healthy control: small corner panel) | overlay really on screen (against the reference picture); a flat-centre heuristic is recorded as information only | **primary** (see findings) |

Occlusion, missing and hidden areas, wrong materials and partial loads are **injected into the scene by QA hooks in `godot/main.gd`** (active only with `--scenario`, never in a normal start; the Rust world and the renderer are not touched). They test whether a detector finds a known defect; they are not defects of the game.

## Not generated (no API for it, so no fake test)

Collision and camera penetration, moving into an obstacle or along a wall (the client has no collision or physics query; the camera is free), overhangs seen from below (WorldGen has none; "looking up" sees sky), editing on a brick boundary (the adapter exposes no brick coordinates or ray hit), Core hash (not exposed), inside-surface occlusion and display-order bugs (no such path), absolute camera coordinates (only relative moves exist). `--checks collision` is accepted and reported as unsupported. The full list is `scenario_gen.UNSUPPORTED`.

## Findings from the real Godot runs

1. **One removed block is invisible from the default camera**: 0 changed pixels (27 batches rebuilt). From a steeper, lower camera it changes 0.2 % of the frame. Edit scenarios therefore use the closer camera; the check warns (not fails) if batches were rebuilt but the picture did not change.
2. **A "centre is one colour" test of occlusion is wrong**: it called the healthy control (small corner panel) blocked, because flat ground fills the middle of the picture (83 % one colour). It is kept as information only; whether a single picture has a blocked centre is left to the visual judge. This is also why all four occlusion templates are `primary`.
3. **Some injected faults are not visible** (a `missing_brick` that changed 0 pixels): the scenario is marked UNKNOWN and not sent to TypeSafe, by the same pre-registered 0.2 % rule as v2.
4. **Persistence and restore are exact on pictures**: after closing and reopening the world the picture differs in 0.00000 of the pixels, for an unedited world and for a world with 5 removed blocks that changed 27 % of the frame.
5. **Two independent executions of the same command gave identical fingerprints, statuses and metrics.**

## Question templates

`questions/v3/templates.json`, versioned, never generated by a model at run time. Every question has a stable id (`Q-TERR-GAP-001`), version, Jev primitive (noul or choice; Box is not used: it needs rework), image slots, an observable criterion, the expected interpretation, a confidence policy (yes >= 0.7, no <= 0.3, in between unsure, unsure is UNKNOWN), the category, and the link to the scenario (`typesafe.questions[].qid`). Five templates reuse the **frozen v2 wording** (a test checks they are identical to the v2 files, so the v2 measurements still describe them); three are **new and uncalibrated** (`Q-CAM-TOP-001`, `Q-CAM-SKY-001`, `Q-OCC-CENTER-001`) and are labelled so in every report. No question asks about invisible state, and none asks about "cracks".

## Routing and statuses

ADAPTIVE (default): TypeSafe is asked only where the template's role is `primary` (visual-only) and the deterministic result is not FAIL and the injected fault is visible; scenarios that code already decides are not sent unless `--compare` or `--force-typesafe`. SINGLE and BATCH send every scenario that has questions.

Statuses: PASS, WARN, FAIL, UNKNOWN, SKIPPED. For an injected-fault scenario the expectation is that the fault is found; the status says whether the observation matched it. **TypeSafe never makes a FAIL**: a clear disagreement is WARN, an unsure answer, a missing answer or an infrastructure error (HTTP 529, timeout) is UNKNOWN. If a scenario can only be judged visually (`needs_visual`) and TypeSafe did not confirm it, the final status is UNKNOWN, not PASS.

## Batching (SINGLE / BATCH / ADAPTIVE)

Limits used (docs.typesafe.ai images and models pages): 32 MiB request body (we plan to 30), 280..1568 px per side, 16 MiB per image, every asset referenced exactly once, **jev-1.14.0: 32k tokens of context per question, and every question sees the whole state, so all images of one request count against it**. We plan to 80 % (25,600 tokens). Tokens per image are an **estimate** (about 3 tokens per 1000 pixels, from v1/v2: 2,910 input tokens for one 1280x720 image with questions); the report compares estimate and measured usage after a live run. A 1280x720 picture is about 2,760 estimated tokens, so about 8 to 9 pictures fit in one request.

- **SINGLE** puts everything into one request, or refuses with "does not fit ... Nothing was sent" (it never builds an invalid request).
- **BATCH** packs whole scenarios greedily in order by estimated tokens, image count and body size (or a fixed `--batch-size`); a scenario's before/after images and all its questions stay together, question names are `<scenario>__<question id>` and image keys `<scenario>_<phase>_<picture>`, so every answer maps back to its scenario and ground truth.
- **ADAPTIVE** = routing, then BATCH on the routed scenarios.

**Not measured, not claimed:** whether one merged request is cheaper or more accurate than several, and whether many images in one state change answers (each question sees all of them). `suite.compare_runs` compares two runs of the same questions (verdict flips, probability differences, tokens, requests, errors) for when that is measured.

## Spend guard

Dry run by default; `--live` required; key only from the environment or the ignored `.env`, never printed or saved (a test greps every saved file, including a deliberately leaked error text); saved requests contain `Bearer <redacted>`. One attempt per request, no automatic retry. A ledger (`ledger.json`) records every request **before** it is sent: an answered request is reused from disk on a re-run (no cost), one that failed or whose result was lost is **not** repeated unless `--retry-errors`. `--max-requests`, `--max-input-tokens` (estimate), `--timeout`. A failed request makes all its scenarios UNKNOWN with the error class (`infra:overload_529`, `infra:timeout`, `infra:rate_limit_429`, `request_rejected`); a response that lacks some answers makes only those scenarios UNKNOWN.

## Limits

Small, controlled scenarios (6 camera, 6 world, 4 editing, 4 occlusion templates); most faults are injected, not natural; the first two TypeSafe results for occlusion do not exist yet; Godot must be installed and a window opens for a few seconds per phase (about 3 s per phase); regression failures saved with `--save-failures` go to `regression/failures/` and are replayed by `--profile regression`. `cube_visual_qa.py` gained the `suite` subcommand after `FROZEN.json` was written, so its hash there no longer matches; the v2 code paths are unchanged and the frozen questionnaires, labels and report code are untouched.
